# Box86 16K-page support for Raspberry Pi 5

This fork carries two complementary layers for running 32-bit i386 software through Box86 on Raspberry Pi 5 systems using a 16 KiB kernel page size:

1. Box86 guest-side ELF/mprotect fixes for 4K-oriented i386 binaries.
2. A private 16K-compatible ARMHF native-library runtime for libraries used by Box86 wrappers.

The Box86 runtime patch series is based on upstream commit `0579f8b9c47d87d700724f4cce559b06cbd2b0f5` and ports newer non-4K ELF32 behavior from Box64/Box32 back to Box86.

## Original reproduced failure

```text
host page size: 16384
Illegal Opcode 0x309e9f8a: FF FF FF FF FF FF
```

The same address and bytes were reproduced with both `BOX86_DYNAREC=0` and `BOX86_DYNAREC=1`, placing the original fault below the dynarec/interpreter split.

## Runtime patch set

- `patches/16k/0001-elfloader-non4k-host-pages.patch`
  - preserves guest-visible 4K-aligned ELF addresses while backing them with host-page-aligned mappings;
  - maps unaligned PT_LOAD segments when virtual/file offsets share the same host-page offset;
  - handles several 4K ELF segments sharing one 16K host page;
  - defers final host-page protection until every PT_LOAD sharing a host page has been populated.
- `patches/16k/0002-mprotect-4k-guest-on-large-host.patch`
  - accepts normal 4K i386 guest `mprotect()` boundaries;
  - rounds actual host calls to the host page size;
  - preserves permissions needed by neighboring guest sub-pages;
  - keeps Box86 protection/dynarec tracking synchronized.

The loader logic is derived from the mature non-4K Box32 implementation in Box64, notably Box64 commits `61d01a4c2c7220b57952b83c270df3f058180095`, `b5d45778c437961a3d7042a680acf33d980f05ff`, and the large-host-page protection work in `9c11c5671c6d385357321856ff75894afab4ee5f`.

## Raspberry Pi 5 build profile

The Debian package builds Box86 with upstream's existing `RPI4ARM64` profile. That profile emits ARMv8-A+CRC AArch32/armhf code compatible with the Raspberry Pi 5 Cortex-A76. The 16K correctness work is in the loader/protection paths rather than CPU tuning.

## Build the Box86 armhf package

On Debian 13 / Raspberry Pi OS arm64:

```bash
./scripts/install-box86-16k-build-deps-debian13.sh
./scripts/build-box86-16k-deb.sh
```

The builder creates a clean worktree at the pinned upstream commit, applies `patches/16k/*.patch`, installs the custom Debian packaging, and writes the resulting `box86-16k_*_armhf.deb` to `dist/`.

## Validated guest-side behavior

On a Raspberry Pi 5 running with `getconf PAGESIZE` = `16384`, the synthetic regression executes successfully:

```text
BOX86_16K_ELF_OK
PASS: 4K-aligned ELF32 PT_LOAD segments execute on host page size 16384
```

The Steam-specific regression also progresses through Steam update installation and no longer reproduces the original `0x309e9f8a / FF FF FF FF FF FF` failure.

## Native ARMHF 16K runtime layer

Full Steam startup exposed a second, separate issue: Box86 wraps selected native ARMHF libraries, and the host dynamic loader rejects ARMHF DSOs whose PT_LOAD layout is only 4K-compatible.

A recursive Debian 13 / Pi 5 audit found 15 incompatible ARMHF SONAMEs. Four low-level source packages have already been rebuilt and validated on the 16K host:

```text
zlib
libbsd
libxau
libxcb
```

The generic Mesa Gallium package itself had 16K-compatible PT_LOAD layout, but its broad driver build reached incompatible `libLLVM.so.19.1` and `libelf.so.1`. The current design removes that generic-driver closure instead of rebuilding LLVM and elfutils.

For Raspberry Pi 5 the private graphics layer builds:

```text
Mesa Gallium: v3d only
Mesa Vulkan:  broadcom (V3DV) only
LLVM:         disabled
GLVND:        private 16K build
```

The Pi-specific Mesa source is fetched from the Raspberry Pi archive, and Debian Trixie's `25.0.7-2+deb13u1` CVE-2026-40393 backports are layered onto that source before building. The builder fails rather than silently using a pre-security source tree.

All resulting libraries are assembled into:

```text
/usr/lib/box86-16k/native16k
```

inside the separate package:

```text
box86-armhf16k-runtime
```

This package does not replace `/usr/lib/arm-linux-gnueabihf`; the private closure is used only by `steam16k`/Box86.

Typical continuation after the validated low-level stages:

```bash
bash scripts/armhf16k-bootstrap-debian13.sh
START_AT=mesa-pi5-private bash scripts/armhf16k-build-all.sh
bash scripts/armhf16k-install-targets.sh
```

Installation verifies every ARM ELF and then runs a freshly compiled 16K-linked ARMHF `dlopen()` harness against GLVND, Mesa, Gallium/V3D, XCB and zlib through the real host dynamic loader. Steam is the next integration test only after that direct host-loader test passes.

See `armhf16k/README.md` for the detailed workflow and `armhf16k/baseline-debian13-pi5.tsv` for the original machine audit.

## Installed package layout

```text
/usr/lib/box86-16k/bin/box86
/usr/lib/box86-16k/native16k/        # when box86-armhf16k-runtime is installed
/usr/bin/box86-16k
/usr/bin/steam16k
/usr/bin/box86-16k-status
/etc/binfmt.d/box86.conf
/etc/box86.box86rc
/usr/lib/box86-16k/tests/
/usr/lib/box86-16k/tools/armhf16k-audit.py
/usr/share/box86-16k/armhf16k-manifest.tsv
/usr/share/box86-16k/armhf16k-baseline-debian13-pi5.tsv
```

The `steam16k` launcher deliberately preserves caller-provided Box86 isolation variables. Box86's standard rc database is installed so Steam receives its upstream `BOX86_NOGTK`, strong-memory, callret, and emulated-library profile. In package `+16k7`, `steam16k` also detects and prefers the private native16k runtime when installed.

## Validation status

The Box86 guest-side 16K implementation and the original Steam illegal-opcode regression are validated on the Raspberry Pi 5. The low-level ARMHF16K zlib/libbsd/libXau/libxcb rebuilds are also validated. The new Pi5-specific Mesa + private GLVND closure is implemented and ready for testing/validation on the same machine.
